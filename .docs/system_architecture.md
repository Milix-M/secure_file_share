## **2\. システム概要**

* **システム名**： 揮発性セキュアファイル転送システム "Ephemeral Pod"
* 目的：
  クライアント側で暗号化を完結させ、サーバ側ではRAM（メモリ）上のみで一時的にファイルを保持することにより、最高レベルの機密性と揮発性（電源断・接続切断による復元不可能性）を担保したファイル共有手段を提供する。
* 適用範囲：
  パスワード、APIキー、機密メモ、小容量の機密文書など、第三者による傍受・復元リスクを最小限に抑えたいデータの1対1共有。

## **3\. システム構成**

### **3.1 システムアーキテクチャ**

### 全体構成図（概念フロー）

1. **送信者 (Client-A)**: ブラウザにてファイル選択 → Web Crypto APIで暗号化（**キーA**を生成）。
1. **サーバ (Go Backend)**: アップロードされた「暗号化データ」を受信 → OSのRAMディスク領域 (tmpfs) もしくは `/dev/shm/ephemeralpod`（デフォルト）に一時保存 → ファイルへの一意なID（**ID-B**）を生成し、送信者に返却。
1. **送信者 (Client-A)**: ブラウザ（JavaScript）が、受信した**ID-B**と自身が持つ**キーA**、およびアップロード元ファイル名を組み合わせ、最終的な共有URLを**クライアント側で組み立てる**。

  * URL例: https://.../download/**ID-B**\#key=**キーA**&name=**ファイル名**

1. **送信者 (Client-A)**: 組み立てた共有URLを受信者に安全な別経路（チャット等）で通知。
1. **受信者 (Client-B)**: 共有URLにアクセス。

  * ブラウザはURLの https://.../download/**ID-B** の部分のみをサーバにリクエストする。**\#**（ハッシュ）以降の**キーA**は、**Webの仕様上サーバに送信されない**。

2. **サーバ (Go Backend)**: **ID-B**に基づき、メモリ管理テーブルからメタデータを検索。受信者ブラウザからのAPIリクエストに応じて残存TTL等を返却し、ダウンロード操作時に**WebSocket接続**を確立。
3. **サーバ (Go Backend)**: WebSocket接続を確認後、「暗号化データ」をストリーミング送信。
4. **受信者 (Client-B)**: ブラウザがデータ受信 → JavaScriptがURLの**\#**以降（**キーA**）を読み取り、Web Crypto APIで復号 → ファイルをダウンロード。
5. **サーバ (Go Backend)**: WebSocket切断（ダウンロード完了、ページ離脱、NW切断）を検知 → RAMディスクから**ID-B**のファイルを即時削除。

起動直後に `EPHEMERALPOD_STORAGE_PATH` 配下へ残っていたファイルは全削除され、過去セッションの断片が残留しないことを保証する。

### ハードウェア構成

* **Web/APサーバ**
  * CPU: 汎用スペック
  * **メモリ(RAM):** 12GB
  * **ストレージ (Disk):** 100GB
  * **スワップ:** OSレベルでスワップ領域を完全に無効化する。

### ソフトウェア構成

* OS: Linux （tmpfs利用 スワップ無効化設定が容易なため）
* バックエンド: Go（chi + gorilla/websocket）
* フロントエンド: Astro
* クライアント: Chrome, Edge, Firefox Stable最新バージョンを想定 (Web Crypto API, WebSocket対応必須)

### ネットワーク構成

* 全通信をHTTPS (TLS 1.3以上) で暗号化。
* WebSocketプロトコル (WSS) を利用。
* CORS許可オリジンは `EPHEMERALPOD_ALLOWED_ORIGINS` で制御し、不要なオリジンからのブラウザアクセスを遮断する。

## **4\. 機能仕様**

* **主要機能一覧**：
  1. ファイルアップロード機能（クライアント暗号化）
  2. 共有リンク生成機能（クライアント側でのURLアセンブル）
  3. ファイルダウンロード機能（クライアント復号）
  4. 接続監視・自動削除機能
* **機能詳細**：
  * **機能1： ファイルアップロード機能**
    * 説明: ユーザーがファイルをWeb UIにドラッグ＆ドロップすると、ブラウザ（JavaScript）がローカルでファイルを暗号化（AES-GCM等）する。この際、**暗号化キー**もブラウザ内で生成・保持する。暗号化されたデータのみをサーバに送信する。
  * **機能2： 共有リンク生成機能**
    * 説明: サーバはアップロードされた暗号化ファイルに一意のファイルIDを割り当て、RAMディスク（`EPHEMERALPOD_STORAGE_PATH` 環境変数で変更可能）に保存し、**ファイルIDのみ**をクライアント（送信者ブラウザ）に応答する。
    * **URLアセンブル**: クライアント（送信者ブラウザ）は、サーバから受け取った「ファイルID」と、機能1で生成・保持していた「暗号化キー」、アップロード元ファイル名（存在する場合）を使い、最終的な共有URLを**クライアント側で**組み立てる。
    * **URL形式**: https://\[ドメイン\]/download/\[ファイルID\]**\#**key=\[暗号化キー\]&name=\[元ファイル名\]
    *  **URLハッシュ（フラグメント）の特性**
      * URLの\#（ハッシュマーク）以降の文字列（フラグメント）は、Webブラウザの仕様上、**サーバへのHTTPリクエストに含まれない**。
      * この特性を利用することで、復号キーはクライアント（送信者）からクライアント（受信者）へ、サーバを一切経由せずに（サーバに知られることなく）受け渡される。これにより、真のエンドツーエンド暗号化が実現される。
    * **ファイル名の扱い**: ファイル名はURLハッシュの `name` パラメータとして埋め込み、受信者ブラウザのみが参照する。サーバ側ストレージおよびログには保存されない。
  * **機能3： ファイルダウンロード機能**
    * 説明: 受信者が共有リンクにアクセスすると、ブラウザはAstroフロントエンドが提供するダウンロードページを取得し、初期表示時にバックエンドの REST API (`GET /download/{file_id}`) を呼び出して暗号化ファイルのメタデータ（残存TTL・サイズ）を取得する。その後、ブラウザ上で動作するJavaScriptが**URLハッシュから復号キー/ファイル名を取得**し、ユーザー操作で復号処理を開始する。
  * **機能4： 接続監視・自動削除機能**
    * 説明: 受信者がダウンロードページを開くと同時に、サーバとの間でWebSocket接続を確立する。サーバはWebSocket接続が維持されている間のみ、RAMディスク上のファイルへのアクセスを許可し、データを送信する。
    * **削除トリガー**: (1) 受信者がファイルを正常にダウンロード完了した時、(2) WebSocket接続が切断された時（ブラウザを閉じる、ネットワーク切断、タイムアウト等）。
    * **削除処理**: サーバはトリガー検知後、RAMディスク (tmpfs) 上の該当ファイルを即時削除する。
    * **容量監視**: 新規アップロード時に論理的な空き容量が不足する場合、アップロード日時の古いファイルから順に自動削除して容量を確保する（デフォルト上限 12GB）。
* **入力データと出力データ**：
  * 入力: 任意のファイル（ただしサイズ上限あり）
  * 出力: 共有URL（送信者）、復元されたファイル（受信者）
* **画面・UI設計**：
  * **トップページ（アップロード画面）**: ファイルをドラッグ＆ドロップするシンプルな領域。
  * **共有リンク発行画面**: 生成された共有URL（コピーボタン付き）と、注意事項（「このURLは一度しか発行されません」「相手がダウンロードするとファイルは消去されます」等）を表示。
  * **ダウンロード待機画面**: (受信者側) 共有リンクアクセス時に表示。「ダウンロード準備中...」
  * **ダウンロード実行画面**: (受信者側) WebSocket接続確立後、「ダウンロード開始」ボタンを表示。ボタン押下でダウンロード開始。

## **5\. 非機能要件**

* **パフォーマンス要件**：
  * **最大ファイルサイズ: 200MB** （`EPHEMERALPOD_MAX_UPLOAD_SIZE_MB` で変更可能。デフォルト200MB）
  * **ファイル有効期限: 30分** （`EPHEMERALPOD_UPLOAD_TTL` で変更可能。例: `8h`）
  * **総保持容量: 12GB** （`EPHEMERALPOD_STORAGE_CAPACITY_MB` で変更可能。超過時は古いファイルから自動削除）
  * **同時接続数の目安**: RAM割当と実測に依存。最大ファイルサイズ想定時は約45セッションを参考値とする。
* **セキュリティ要件**：
  * **クライアント側暗号化**: Web Crypto API (AES-256-GCM) を使用する。
  * **通信経路**: 全通信をHTTPS (TLS 1.3) で強制する。
  * **サーバ側（データ非保持）**:
    * **スワップ領域の完全無効化**をOSレベルで設定・担保する。
    * **RAMディスク (tmpfs)** のみを使用し、いかなる場合も永続ストレージにファイルデータを書き込まない。
    * サーバプロセスは最小権限で実行する。
  * **サーバ側（キー非保持）**:
    * **「URLハッシュの特性」**（4. 機能仕様参照）により、**復号キーは技術的にサーバ側で受信・保持することが不可能**な設計とする。
  * **HTTPセキュリティヘッダー**: APIレスポンスに `Content-Security-Policy`, `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options`, `Permissions-Policy` を付与し、ブラウザ通信面での攻撃面を最小化する。
  * **その他**: XSS, CSRF等の基本的なWeb脆弱性対策を講じる。
* **可用性・信頼性**：
  * 本システムの特性上、サーバの再起動やクラッシュ時はRAM上の全データが失われる（仕様）。これは障害ではなく、揮発性という目的を達成する正常な動作と定義する。
  * サービス自体（アップロード機能）の稼働率は99%を目指す。
* **拡張性・保守性**：
  * APサーバはステートレス設計とし、ロードバランサによる水平スケール（台数を増やす）を可能にする。（ただし、RAMディスクは各サーバローカルのため、スティッキーセッションが必要になる）

## **6\. インターフェース仕様**

* **外部システムとの連携**： 原則として無し。
* **API仕様（RESTful \+ WebSocket）**：
  * `POST /api/upload`
    * リクエスト: multipart/form-data（フィールド名 `file`）暗号化済みバイナリを送信。
    * レスポンス: `{ "file_id": "...", "size": <bytes>, "ttl_seconds": <秒>, "expires_at": <RFC3339> }`
    * 代表的なエラー: 413（`EPHEMERALPOD_MAX_UPLOAD_SIZE_MB` 超過）、507（`EPHEMERALPOD_STORAGE_CAPACITY_MB` 超過）
  * `GET /download/{file_id}`
    * リクエスト: JSONヘッダー不要。認証なし。
    * レスポンス: `{ "file_id": "...", "size": <bytes>, "ttl_seconds": <秒>, "expires_at": <RFC3339> }`
    * 注意: このエンドポイントは暗号化データ本体を返さず、Astro側のダウンロードページから呼び出される。
  * `GET /download/{file_id}` (フロントエンド)
    * Astroが提供するHTML/JS。URLハッシュはここでのみ利用され、バックエンドへは送信されない。
  * `WSS /ws/connect/{file_id}`
    * 接続確立後に暗号化データをストリーミング送信。完了後、サーバから正常終了コード(CloseNormalClosure)を送信し、ストレージを即時削除。
* **データベース設計**：
  * **原則としてデータベース（RDB/KVS）を使用しない。**
  * 理由: データベースに書き込むと永続化されてしまい、「電源断で復元不可」の原則に反するため。
  * ファイルIDとRAMディスク上のファイルパスの紐付けは、Goバックエンド内の`storage.Manager`が`map`で管理する。

* **環境変数（抜粋）**：
  * `EPHEMERALPOD_ADDR` – HTTP待受ポート。デフォルト`:8080`
  * `EPHEMERALPOD_STORAGE_PATH` – 暗号化ファイル保存先。デフォルト`/dev/shm/ephemeralpod`
  * `EPHEMERALPOD_STORAGE_CAPACITY_MB` – 保存領域の論理上限。デフォルト`12288`（12GB）。不足時は最古のファイルから自動削除。
  * `EPHEMERALPOD_MAX_UPLOAD_SIZE_MB` – 最大アップロードサイズ。
  * `EPHEMERALPOD_UPLOAD_TTL` – ファイル有効期限（期間文字列）。
  * `EPHEMERALPOD_CLEANUP_INTERVAL` – 期限切れファイルクリーンアップ間隔。
  * `PUBLIC_API_BASE` / `PUBLIC_WS_BASE` – フロントエンドからのAPI/WS接続先を指定（開発・本番双方で利用）。
  * `EPHEMERALPOD_ALLOWED_ORIGINS` – CORS許可オリジン。カンマ区切り。空または未設定の場合はワイルドカード(`*`)。

## **7\. 運用・保守**

* **監視・障害対応**：
  * **RAM使用率の監視**: 最重要項目。閾値（例: 80%）を超えたらアラート。
  * WebSocket接続数、アクティブセッション数の監視。
  * **スワップが無効になっていること**の定期的な確認（OS監視）。
* **バックアップ・リカバリ**：
  * **データバックアップは一切行わない**（システムの目的に反するため）。
  * リカバリ対象は、サーバOSとアプリケーションコードのみとする。
* **バージョン管理**： Gitを使用する。
* **ログ管理**：
  * **ファイル内容、ファイル名、IPアドレス、ファイルID、復号キー等**の機密情報は、原則としてログに一切記録しない。
  * エラーログ、アプリケーションの稼働状況（起動、停止）など、運用に必要な最小限のログのみ記録する。

## **8\. テスト計画**

* テスト方針：
  セキュリティ要件（キー非保持、データ揮発性）を最重要項目としてテストする。
* **テストケース（抜粋）**：
  * **機能テスト**:
    * 暗号化・復号が異なるブラウザ間（Chrome, Firefox, Safari）で正常に行えること。
  * **セキュリティテスト（キー非保持）**:
    * **サーバのアクセスログ、アプリケーションログに、復号キー（\#以降）が一切記録されていないこと。**
    * サーバ側のネットワークキャプチャ（パケット監視）を行い、HTTPリクエストに\#以降が含まれていないことを確認する。
  * **セキュリティテスト（データ非保持）**:
    * サーバの永続ストレージにいかなるファイル断片も残っていないこと。
    * サーバ再起動後、データが完全に消去されていること。
  * **揮発性テスト**:
    * ダウンロード完了後、ファイルが即時削除されること（再度同じURLにアクセスしても404となること）。
    * WebSocket切断（ブラウザタブ閉じ、ネットワーク切断）で、ファイルが即時削除されること。
  * **負荷テスト**:
    * 最大ファイルサイズのアップロード/ダウンロードテスト。
    * 多数の同時接続を行い、RAM使用率とパフォーマンス低下を測定する。
* **受け入れ基準**：
  * 上記テストケースをすべてクリアすること。
  * 特に「スワップが発生しないこと」「サーバ再起動後にデータが残存しないこと」「サーバ側でキーを一切受信しないこと」が確認できること。
